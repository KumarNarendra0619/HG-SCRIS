# BUILD-04L — Model Governance, Uncertainty, Provenance, Validation & Reproducibility Control Layer

## Purpose
Provide the control layer that makes every HG-SCRIS dataset, reconstruction, network trace, hazard result, exposure estimate, evacuation result and visualization auditable and reproducible.

## Core principle

`NO RESULT WITHOUT LINEAGE`

A result must be traceable to its inputs, method, parameters, software/model version, execution environment and validation status.

## Governance chain

```text
DATASET
  ↓
DATA VERSION
  ↓
METHOD VERSION
  ↓
MODEL VERSION
  ↓
PARAMETER SET
  ↓
RUN
  ↓
VALIDATION
  ↓
UNCERTAINTY
  ↓
RESULT
  ↓
PUBLICATION / VISUALIZATION
```

## 1. Dataset governance

Each dataset receives a stable dataset_id and version.

Minimum metadata:

- dataset_id
- version
- provider/source
- acquisition/reference date
- spatial/temporal coverage
- CRS
- license/access conditions
- processing status
- checksum/hash where practical
- provenance record
- quality status

Raw source data are immutable. Derived products reference their parents.

## 2. Method registry

Every analytical method is registered independently of the data.

Minimum fields:

- method_id
- method_name
- version
- purpose
- process/domain
- inputs
- outputs
- assumptions
- parameter schema
- limitations
- validation evidence
- implementation reference

Changing a material assumption creates a new method version rather than silently replacing the old one.

## 3. Model registry

Every numerical model records:

- model_id
- model family
- process type
- version
- implementation/source
- required inputs
- assumptions
- parameter definitions
- spatial/temporal resolution
- calibration status
- validation status
- known limitations

A model cannot be marked validated merely because it executes successfully.

## 4. Run manifest

Every execution receives a unique run_id.

Minimum run manifest:

```text
run_id
event_id
scenario_id
dataset_versions
method_versions
model_versions
parameter_set_id
software_version
code_commit
environment/dependency lock
execution timestamp
operator/origin
input hashes where practical
output hashes where practical
validation_status
uncertainty_status
```

## 5. Provenance graph

Represent analytical lineage as a directed acyclic provenance graph wherever the workflow permits:

```text
SOURCE DATA
   ↓
TRANSFORMATION
   ↓
DERIVED DATA
   ↓
MODEL INPUT
   ↓
MODEL RUN
   ↓
RESULT
   ↓
MAP / REPORT / ANIMATION
```

Relationships must distinguish `derived_from`, `used_by`, `validated_against`, `visualized_as` and `supports_claim`.

## 6. Validation framework

Validation status must be explicit:

- NOT_TESTED
- QA_PASSED
- CALIBRATED
- VALIDATED
- PARTIALLY_VALIDATED
- FAILED
- NOT_APPLICABLE

Data QA, model calibration and independent validation are separate concepts.

Where multiple historical events are available, calibration and validation events should be separated. A single-event fit must not be described as independent validation.

## 7. Uncertainty framework

Classify uncertainty sources:

- measurement uncertainty
- positional/spatial uncertainty
- temporal uncertainty
- classification uncertainty
- parameter uncertainty
- model structural uncertainty
- scenario uncertainty
- exposure uncertainty
- vulnerability uncertainty

Do not collapse these into a single numerical uncertainty score unless a defensible statistical method is specified.

## 8. Confidence vs uncertainty

Confidence describes the evidential support for a claim. Uncertainty describes what remains unknown or variable.

Therefore maintain separate fields:

```text
confidence_status
uncertainty_status
uncertainty_sources
```

## 9. Claim-level evidence control

Scientific claims generated by the system should be linked to supporting evidence/results.

Example:

```text
CLAIM-001
  ↓ supported_by
EVIDENCE-014
EVIDENCE-021
MODEL-RUN-008
```

The system must distinguish direct observation from inference and model output.

## 10. Historical / modelled / scenario separation

Every result must carry a state:

- OBSERVED
- RECONSTRUCTED
- MODELLED
- SCENARIO
- DERIVED
- SYNTHETIC/TEST

These states must remain visible in research exports and visualization metadata.

## 11. Reproducibility levels

Use explicit reproducibility grades:

### R0 — Narrative only
Insufficient machine-readable lineage.

### R1 — Data reproducible
Input datasets and versions identified.

### R2 — Processing reproducible
Transformation method and parameters recorded.

### R3 — Computationally reproducible
Code, dependencies and run configuration recorded.

### R4 — Independently reproducible
An independent execution reproduces the published result within documented tolerances.

Do not claim R4 without an independent reproduction check.

## 12. Quality gates

### Gate A — Data QA
Schema, geometry, CRS, completeness and temporal validity.

### Gate B — Method QA
Method implementation and assumptions reviewed.

### Gate C — Model QA
Numerical execution, stability and boundary-condition checks.

### Gate D — Scientific validation
Comparison with independent observations/events where available.

### Gate E — Publication QA
Final map/table/report checked against the exact run and data versions.

## 13. Audit trail

Immutable or append-only audit records should capture:

```text
actor/source
operation
timestamp
object_id
old_version
new_version
reason
run_id
```

Do not silently overwrite analytical results.

## 14. Change management

Material changes to:

- data
- algorithms
- model equations
- parameter defaults
- classification thresholds
- routing rules
- vulnerability weights
- visualization interpretation

must generate a new version and invalidate dependent cached products where necessary.

## 15. Result certification

A result can carry one of:

```text
DRAFT
QA_PASSED
RESEARCH_READY
VALIDATED
PUBLISHED
SUPERSEDED
RETIRED
```

`PUBLISHED` does not automatically mean scientifically validated; certification state and validation state remain separate.

## 16. Reproducibility package

For a research result, package:

- data manifest
- method manifest
- model manifest
- parameter manifest
- run manifest
- code commit
- dependency/environment specification
- validation report
- uncertainty report
- output checksum
- README/reproduction instructions

Large source/model datasets should be referenced through appropriate versioned storage rather than committed into Git history.

## 17. Automated integrity checks

The control layer should test:

- missing lineage
- broken parent references
- duplicate IDs
- missing version
- orphaned outputs
- incompatible dataset/model versions
- unregistered methods
- parameter schema violations
- stale cached products
- result without run_id
- published result without validation status

## 18. Governance rule for AI assistance

AI-generated interpretations, classifications or summaries are never treated as primary evidence. AI outputs must reference the underlying evidence/data and remain labelled as machine-assisted interpretation where applicable.

## 19. Research audit dashboard

The future UI should expose:

```text
Result
 ↓
Data
 ↓
Method
 ↓
Model
 ↓
Parameters
 ↓
Run
 ↓
Validation
 ↓
Uncertainty
```

A researcher should be able to answer: `Why did this result occur?` without inspecting application source code.

## 20. Acceptance gate

BUILD-04L is complete when every production analytical result can be traced to versioned inputs and methods; model and validation status are explicit; uncertainty is documented; material changes create new versions; audit records are preserved; and a reproduction package can be generated for a selected result.
